# Codex DeepSeek Bridge v0.1.0 — final release report

Historical snapshot: the later [2026-09-25 field closeout](FINAL_CLOSEOUT_2026-09-25.md) records real SnakeBattle jobs over 300 seconds. It supersedes only the time-bound statement below that no such field endurance had yet been measured; the short scripted reconnect and long field runs remain separate evidence.

This report is based on the release implementation commit `f136a37a4064fc0c5dfc70ee8b8d09b699764a29`. The report-only commit and annotated tag are resolved with `git rev-parse v0.1.0^{commit}` after publication; a file cannot contain its own Git SHA without changing that SHA.

1. **Final commit SHA:** implementation commit `f136a37a4064fc0c5dfc70ee8b8d09b699764a29`; the release tag will identify the final report commit.
2. **CI:** [GitHub CI run #16](https://github.com/zadyqs/codex-deepseek-bridge/actions/runs/36084267201) passed on both Ubuntu and Windows for the implementation commit.
3. **Previous CI root cause:** run #15 failed in `Run core offline tests` on both systems. Ubuntu asserted a hard-coded `C:` path; Windows compared an 8.3 temp path with Git's long path as if their strings must match. Tests now use a platform-native real path and a platform-local nonexistent path; no safety assertion was removed.
4. **Synchronous timeout root cause:** `run_parallel` blocks on worker completion. Raising its internal `timeout_seconds` does not extend an outer MCP/tool call. SnakeBattle observed several 240/260/300-second request windows and partial edits; the experiment report specifically confirmed one 240-second request-side self-limit. A universal host-side 300-second limit was *not* independently established.
5. **Long-job architecture:** `submit_jobs` returns promptly after creating a private job record and launching a detached local Node supervisor. The supervisor runs bounded Codex workers and atomically persists progress/results independently of the MCP server process. This is local single-user supervision, not a distributed queue.
6. **Interfaces:** `submit_jobs`, `get_job_status`, `collect_results`, `cancel_job`, plus `list_jobs` for bounded ID recovery. The original `run_parallel` remains available and behavior-tested.
7. **Persistence:** `~/.codex-worker-bridge/jobs/<job_id>/` (Windows under `%USERPROFILE%`). Durable `job.json` includes schema version, IDs, times, workspace, requests, per-task status/PID/thread/attestation, bounded event progress, results, cancellation/failure details. The private launch payload containing prompts is removed when the supervisor starts; provider environment variables are not serialized.
8. **Timeouts:** synchronous worker 30–1200s; background `short` 30–600s, `feature` 30–3600s (default one hour), `extended` 30–7200s with an explicit value. No unlimited task is exposed. Worker timeout is `timed_out`; an outer parent/tool timeout is outside the job and should be investigated via `list_jobs`/status.
9. **Cancellation:** `cancel_job` writes a job-specific request; the supervisor aborts queued work and terminates only its worker process trees (`taskkill /T /F` on Windows, process-group kill on POSIX). Existing progress and partial output remain collectable. An unrelated concurrent job is not killed in the fixture test.
10. **Attestation:** child rollout evidence must now include provider, model, reasoning effort, and CLI version. Expected values remain fail-closed; child thread IDs and canonical model ID persist with results.
11. **Model alias:** the explicit display label `DeepSeek V4.1 Flash` and API ID `deepseek-flash` compare as the same canonical model. Unknown friendly aliases, wrong providers, wrong models, and wrong reasoning efforts still fail.
12. **Sandbox/Git:** workers use only `read-only` or `workspace-write`. Sandbox `.git` may be read-only; workers edit/test, while the parent independently reviews, reruns checks, and commits. No privilege relaxation or automatic merge was added.
13. **Automatic tests:** 21 offline tests in three suites (core/jobs 19, MCP server 1, bundled runner 1) passed locally. Fixtures cover submit immediacy, real background continuation, MCP restart, collect repeatability, cancellation/tree cleanup, timeout, provider failure, partial output, concurrency, isolation, traversal, bounds, redaction, attestation persistence, and timeout policy.
14. **Windows/Linux:** local Windows Node 25 full verify and Node 20 core/jobs pass. GitHub CI's Ubuntu and Windows matrix both passed for the implementation commit. No native Linux machine was used outside CI.
15. **Live synchronous DeepSeek E2E:** final candidate version returned 2/2 successful `deepseek` workers, `peakConcurrency=2`, `overlapMs=12967`, exact markers, and `deepseek-flash/high` attestation with Codex CLI `0.155.1`.
16. **Live background DeepSeek E2E:** final candidate version submitted a real job, closed the first MCP client, reconnected, polled, collected `BRIDGE_LIVE_JOB_OK`, and attested `deepseek/deepseek-flash/high`; worker duration was about 16 seconds. This proves lifecycle separation, not a measured >300-second endurance run.
17. **Security checks:** `npm audit --omit=dev --audit-level=high` found 0 vulnerabilities; plugin/Skill validation and `git diff --check` passed. Known credential values in arguments are rejected; results and errors are redacted; raw prompts/keys are excluded from durable metadata. A local job directory still deserves normal user-account protection.
18. **README/case study:** first-page positioning now states the premium-supervisor/external-worker value without promising quota multipliers. Synchronous vs background modes, provider verification boundary, native picker limitation, sandbox governance, official issue links, and a SnakeBattle evidence/interpretation case study are documented.
19. **Remaining limits at the original release-report date:** sudden power loss is not recoverable; no safe per-worker changed-file attribution in a shared workspace; no provider cost accounting unless a reliable API exists; only DeepSeek is live-verified; custom providers do not appear in the native picker; background supervisor survival under every possible host-specific Windows Job Object policy remains to be field-tested. The original report's statement about >300-second live endurance was superseded by the field addendum below.
20. **Release decision:** the v0.1.0 code gate was met: both CI systems passed, synchronous mode remained live-verified, the detached job lifecycle and cancellation passed fixtures, a real DeepSeek background job passed, and security/manifest checks passed. The release tag is the publication marker. The field addendum below adds later endurance evidence without changing that original release snapshot.

Checks used: `npm ci`, `npm run verify`, `npm audit --omit=dev --audit-level=high`, plugin validation, Skill validation, `git diff --check`, `npm run test:e2e`, and `npm run test:e2e-job`. The exact implementation diff is [d0b4f3e...f136a37](https://github.com/zadyqs/codex-deepseek-bridge/compare/d0b4f3e...f136a37).

## 2026-09-25 SnakeBattle field addendum

This later evidence comes from the maintainer's [SnakeBattle field acceptance report](docs/SNAKEBATTLE_CASE_STUDY.md). In one real project, the top-level Codex submitted background work with `submit_jobs`, checked it with `get_job_status`, and collected completed results with `collect_results`. Of 12 real engineering jobs listed, 10 worker durations exceeded 300 seconds; the longest was `1,553,082 ms` (about 25 minutes 53 seconds). These were production tasks, not artificial waits.

For example, job `f819e1b1` returned a queued ID immediately, remained running at about 428 seconds, then succeeded after `431,116 ms`; the parent collected the complete, untruncated result. Its recorded runtime identity was `deepseek / deepseek-flash / high`. The parent found a world-unit versus fixed-point-unit mismatch and held integration; a separate correction job ran `320,285 ms`, after which the parent independently passed the focused 25/25 checks. Job `6204979d` also remained running beyond 300 seconds and later succeeded after `1,553,082 ms`; the parent reran its focused eight tests before committing.

This field run establishes long-job survival and result collection in that project. `list_jobs` recovered an existing job across separate tool calls, but this was **not** an MCP client reconnect. The run did not test client reconnect, Windows shutdown, power loss, worker kill/recovery, or a continuous one- or two-hour task. The short scripted reconnect test described in item 16 is separate evidence. The field attestation was checked against Codex child-task records; it is not a vendor-issued cryptographic attestation.

The worker sandbox's standard `npm test` also hit Node child-process `spawn EPERM` in one task. The worker's single-process fallback produced 195/195; the parent then ran standard `npm test` in its normal environment, strengthened the review checks, and got 196/196 before committing. Later SnakeBattle's own game suite reached 216/216; this is a game-test count, not a Bridge test count. A worker-reported 672 randomized checks were not independently rerun by the parent. No API-cost or premium-usage savings comparison was measured.

The exact installed Bridge binary used for these 12 jobs was not tied to a source commit through immutable build provenance. The field run made no Bridge source changes. See the [final field closeout](FINAL_CLOSEOUT_2026-09-25.md) for the evidence table, installation checks, and remaining boundaries.
